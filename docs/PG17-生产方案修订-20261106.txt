PG17 内存自动伸缩：生产方案修订
日期：2026-11-06
状态：架构决策与实施/验收要求；尚未表示代码已完成或生产验收通过。
范围：只处理PG内存伸缩及其直接影响的Neon组件；由主执行者单独推进。

一、目标与上游基线

官方Neon已具备Compute/VM资源伸缩：Agent决定目标，Scheduler提供资源许可，Monitor判断缩容可否进行，NeonVM Controller/Runner执行VM调整；PG文件缓存可随资源改变。我们新增的价值是PG内核动态共享缓冲区、PG工作域真实硬限的在线调整，尤其安全normal降限。VM变小、RSS下降、固定normal上限均不代表完成本需求。

官方公开协议包含Agent/Monitor健康检查；本项目新增的“远程完整审计必须不断续30秒租约，否则关闭SQL”不能视为上游架构的必然要求。健康检查、操作期限、写者租约、SQL服务安全是不同概念。

二、核心决策：分开资源安全、写入权属与SQL服务

1. 资源安全由持续生效的实际约束保证：PG当前共享内存上界、normal真实硬限、受控系统/外部预算、VM实际内存，以及Scheduler保留的资源。管理进程没有及时回复，不等于这些约束已经失效。
2. 原OwnerLease、PG/Guest/Runner的单调fencing、实例boot/UID、容量代次、原操作ID和持久未知记录继续保护伸缩写入。旧控制器不得写，未知动作不得自动重发或当成NoEffect。
3. 从默认生产路径移除“远程审计续租超时自动关闭SQL”的依赖。不是把30秒改大，也不是删除Unknown门：通信故障应暂停新的内存变更、保持最后安全容量与峰值预留；SQL是否能继续由真实资源状态决定。
4. SQL准入仍用于必要场景：新PG启动尚未完成预算初始化；确有不安全资源状态；安全切换所需的短临界区。正常管理等待不能长期占住临界区或向业务返回统一准入错误。
5. 新安全语义必须通过既有版本/能力协商明确表达。旧记录保持可读，旧镜像不得被默认为支持新语义；不提供一个可绕过安全检查的业务开关。公共合同不按PG17/PG18版本分叉。

三、必须保留的安全边界

A：PG实际共享内存上界；N：normal工作域实际硬上限；B：既有合格外部预算（系统域已包含其中，禁止重复相加）。沿用并核实已有A+N+B不超过Guest可用预算的合同及其实际来源。不能用占用低、自报数字或租约存活替代这些边界。

normal降限只允许在既有内核/Guest机制证明目标安全、原控制边界固定后执行；真实memory.max/相关quota必须生效并读回。不能直接向使用中的不安全目标强写降限、诱发OOM后冒充成功。

Host仍以原Scheduler为唯一容量权威。现有持久记录只增强该权威的重启恢复、在途峰值和结算；不得再产生并行分配器、重复计费或依靠租约超时释放活VM资源。Host范围为明确K8s预算，不新增整机内核绝对上界证明。

四、完整动作顺序

扩容：原Scheduler准入并保留峰值 → VM/Guest容量先到位 → 真实PG工作域硬预算到位 → PG内核增长共享缓冲区 → 回读PG、硬限、VM实际值与数据 → 提交最终预算。现有SQL保持服务。

缩容：PG/Guest先判断能否安全回收 → 淘汰/释放共享缓冲尾部，确认物理释放和代次 → 安全降低normal真实硬限并读回 → 由原Runner/Linux执行并确认VM缩容 → 最后释放Scheduler多余预留。不能先减VM或释放Host，再期待PG自行追上。

固定页、活跃工作、不可安全降低的normal或Linux拒绝热拔，应拒绝/延期本次目标。若已有部分效果，按真实状态收敛并保留足够资源；不能把部分成功算全链成功，也不无条件回滚未知动作。

切换若确需短暂停顿，应由内核/Guest局部协调，保持连接并支持取消/超时；远程来源读取、调度等待和构建过程不得放入业务暂停窗口。

五、失败与恢复统一规则

新Host许可尚未发布、指标暂缺、控制API延迟、Agent短暂失联：冻结伸缩，保持原安全资源和峰值预算。没有不安全中间态且硬约束仍有效时，SQL继续。

写入丢回复：保持原Key/命令/Unknown，只观察原操作的真实状态；不换Key重发、不延长原期限、不提前归还内存。

换Owner：复用原选主和fencing，确认旧写者失权，再从原日志与实际资源接续。SQL服务不应依赖控制器代次本身；PG重启则是新boot，必须重新完成启动预算。

确证硬限失效、实际资源超出安全边界、实例身份变化或不安全的内核中间态：保留必要准入保护并进入受控恢复。不能将“读不到证明”伪装成“证明成功”；暂停伸缩与关闭SQL的判定必须分开。

六、自动策略与统一多版本合同

策略使用真实工作域内存、负载和稳定窗口提出目标；指标只用于决策，不能签发安全许可。增长及时、缩容有稳定窗口和冷却期，失败有退避，目标受已验证规格限制。

普通空闲连接不等于内存不安全；不应为使自动缩容用例通过而要求用户断开所有连接。是否能缩由实际内核/Guest安全机制决定；不支持该能力的旧profile应明确拒绝，而不是降级伪装。

上层只处理期望目标、已确认状态、能力、操作代次和失败原因；PG版本差异封在PG/Compute适配。PG18复用PG17验收后的协议、调度、策略、Runner和恢复逻辑，仅验证必要的内核差异。实验档位不能写死为公共API；未验证规格不提前宣称支持。

七、最小实施范围与版本发布

先核全部直接接线：PG原生准入/失联关门、Compute配置与API、Agent正常循环和恢复、normal额度执行、Scheduler峰值持有/释放、Runner实际容量，以及共享协议的读者。

保留已有效的动态缓冲区、真实normal quota、原fencing与未知对账。纠正全局SQL心跳耦合、将暂时缺新许可混成现有资源失效的路径，以及不必要的零连接前提。复用已有执行器/快照/能力协商，不另造认证、预算或测试框架。

共享合同有变化时，所有读取该合同的必要组件必须一致升级；即使某组件业务逻辑不变，也要核其实际镜像能读取新合同。先升级兼容读者，再启用新写入语义，避免只更新Agent后其他组件拒绝新状态。不扩大测试未修改的上游功能。

内核/Guest需更新时，沿原保数据发布流程处理；保留endpoint、tenant/timeline、MinIO/PVC、凭据和原失败证据。镜像由118构建，经SSH预载117/118/119的实际containerd k8s.io，自有Helm使用准确digest与IfNotPresent，不部署116。

八、验收与停止条件

单元/组件只覆盖新增或改变的合同：新/旧能力识别、预算和代次、正常等待保活、旧写者拒绝、丢回复保Unknown、缩容拒绝/部分效果及实际不安全状态保护。

先完成Linux真实链快速验证，然后三节点Helm环境验收：
1. Grow：PG共享缓冲、实际normal硬限、VM实际容量按目标到位。
2. 安全normal Shrink：真实共享内存释放、N真正降低、VM真正缩小；不以RSS下降代替。
3. Regrow：再次真实增长，资源、代次和数据一致。
4. 自动策略：由真实内存负载变化触发原策略及完整动作；管理Begin不能冒充自动触发。

同一轮需经Proxy持续读写，核原PG实例/连接、提交数据和校验值、相关WAL持久性及每阶段实际资源。只在资源本就已到位时产生的NoOp不能冒充物理扩容。

直接失败用例：管理延迟超过原30秒/暂时失联仍可在有效旧预算下查询；许可等待不写资源；接管后旧命令被拒绝；丢回复不重复执行或提前释放；真正硬约束失效仍被保护。只测这些修改直接影响的行为，不测试K8s平台通用功能、无关CPU/存储/迁移/HA矩阵。

每次失败先用实际阶段、日志、退出状态和资源回读确定首因；同类失败没有覆盖性修复和相关验证前，不重复换Owner/重建试错。阶段按原分支中文提交，归档commit/镜像digest/部署身份/原操作/资源及数据前后证据。

先完成PG17全部内存端到端与归档总结，再PG18端到端。最新完整控制面对接保留总计划的后续目标，本轮不提前扩展控制面业务。只有实际验收通过才发布首版，方案合理不等于版本已经达标。

当前事实：AS87b07a1已推送且三节点部署，Host首次未发布等待修复的直接正负控通过；PG17四项最终内存动作仍未验收。单轮远程审计约26秒、后续更长，2核配置未证明解决根本耦合。当前旧测试实例Owner40/W181处于保护关闭，原数据、资源和失败证据保留。本修订尚未改动原生租约策略，不能声称已解除问题。
