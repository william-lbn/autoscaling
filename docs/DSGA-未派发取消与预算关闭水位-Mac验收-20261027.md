## 问题与实现约定

原计划全部 Planned 时，取消仍会落到 Host 消费者。该消费者拒绝启动已取消的
持有是正确的，但外层因此一直无法写入已有协议的 AbortedBeforeDispatch。
现在实际生产 PGWorker 的首个执行器在领域分流前检查并关闭原意图。

条件必须同时成立：原 owner/VM/PG 绑定一致、VM 可协调、已经请求取消、
全部原步骤 Planned、无 Cleanup、PG/准入/Root SDK 均无未决意图。删除、跨
PG boot、任何 Unconfirmed、已结算/拒绝或已进入清理的计划均不能用此入口。
Finish 使用原 VM UID/RV CAS；并发 Start/接管一旦先提交，旧快照不能覆盖它。
回复丢失保留 unknown，下一轮真实读回同一历史，不重复追加或猜测派发结果。

这个终态只说明原执行链未获派发，不说明所有外部承诺不存在。Scheduler 可独立
准备 Host 持有，本路径保留它；不发送 PG Cancel/准入/Root/QMP，不制造
NoEffect/物理归还，不释放预算、初始节点容量或外部来源，高水位继续保留。

接通后还须解决旧 Host 结清的活性缺陷：旧代码要求 HWM 等于原成功请求，并
依赖最多 16 条终态历史。后续未派发取消或成功历史淘汰会阻止有效预算结清。
当前完整预算保持永久寿命，同时新增永久 `BudgetBoundary`：

- 原成功 Finish 同一 CAS 保存原预算 Key、完整命令摘要、落账/成功关闭序列。
- 只有全部 Planned 的取消可以推进 ThroughKey/ThroughSequence，不改原预算。
- 任何 Start、StartCleanup 在写前 CAS 即撤销该证明；新完整预算也清空它，
  必须重新成功关闭。失败、拒绝、部分完成不能借旧预算跨过已派发效果。
- 接管、结果数量/字节淘汰不丢水位；Clone 不共享指针，严格校验身份、序列、
  仍在历史中的交叉事实。新预算不得把协议版本降回旧版。
- Host 结清检查永久关闭水位后，仍认证原 owner、Runner 出生/原回执/实际值、
  当前预算来源和原 Node，再做原 UID/RV CAS。水位本身不证明物理空闲。

## 格式与兼容边界

首次保存水位升级 **VM Model v5**。Node Model v5、Host CM v2、Runner record/
publication v1 及 PG ABI 不变；两个 v5 属于不同对象，不能混用。
旧程序最高支持 VM v4 或更早，会拒绝新格式。Linux 后验须使用同一批四个服务
源码/产物；不能仅替换 Agent 后继续用旧账本读写者。

旧 VM v4 在显式 Finish 中，只有原成功记录仍完整存在，且其后所有记录均为
未派发取消时，才可原 CAS 升级。普通 Load 不补字段；原成功已过期、夹杂
已派发取消或 v5 证明已被 Start 撤销时均不猜测。此时继续保留峰值，须新一轮
完整验证操作或后续受控恢复，不能通过删 HWM/来源或降级强行回收。

独立控制面保留 `d84c0b73004a7d8cc3e89f3c3f0e3f06cfa8cba9`，本轮未改业务
或 SDK。后续移植必须升级 VM v5 读者并保留完整原身份/来源，再统一 E2E。
