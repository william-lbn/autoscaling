## 完整实际预算的职责与两类 PG 来源

`ServiceActualRecovery` 固定完整原操作/Prepared 摘要、最近准确关闭、原
观察者、当前 PG 成本、完整 Root 来源与 v4 `ReconciledCapacity`。原 Active、
步骤 Unknown/终态审计、Abort、旧永久预算和旧关闭 expected 代次全部保留。
单领域证明仍不授予开放、普通 Finish、缩 VM 或 Host 退还许可。

v4 的 PG 来源严格二选一，不修改普通取消 v1–3 的条件：

| 原 PG 步骤 | v4 来源与不变量 |
|---|---|
| 尚 Planned | 保存完整原 `Prepared.Shared`；原容量代次/前缀及旧终态头必须吻合，SDK 必须没有原 Resize Pending，不能按当前数值把已派发改成未派发 |
| 已派发或已有原终态 | 固定原 `RecoveryPG.Fence/Status`，完整终态与严格更高 floor 隔离分别校验；当前稳定容量只允许原操作有限前后代，原 Unknown 或原生终态审计不可改写 |

当前共享成本须被实际 Root 聚合上界覆盖；未知数组分配、PREPARING、实例/
boot、容量或来源变化均拒绝。原生缓存中的较新同容量终态不是原操作成功。
已保存终态被淘汰时仍保留该完整旧事实，不把它替换成 `isolated_unknown`。
原步骤已保存 Committed/Denied 时，独立实际容量不能反过来否定它；仍有原
完整结果时须逐项一致。原 Guest 已 Applied 时，完整命令/出生/限额须同时
绑定原 Prepared 与真实 Held，不能只比较聚合字节数。

原关闭确认后原 Resize 仍可迟到提交。新证明保存当前实际下一代容量，新
开放/rearm 采用准确实际容量；旧关闭命令及其 expected 代次保持原文。关闭
布尔值、新开放 setter 成功或当前相同容量，都不能替代完整来源审计。

## Outside、Root 与 Guest 可用内存分别取准确来源

Outside 按当前实际 VM 规格选择，normal/HugeTLB 聚合按当前确认 Root 选择。
Guest 未收到原命令并被封存取消，不意味着 VM 也回到旧规格：

| 当前实际 VM | 允许的 Outside 来源 | 可用内存保证 |
|---|---|---|
| 已到原 target | 原 Prepared 的准确 target Outside | 该原资格中 target 的保证值 |
| 仍为 before | 原永久预算的准确 before Outside；首次可用完整原 Initial | 原 before 规格的保证值 |
| 原 VM 从未派发且仍为启动容量 | 原 Initial Outside 与独立 InitialVM 出生来源 | 原 Initial 保证，不合成 Resize/取消/Completed |

旧大 VM 不能借新小规格资格，已扩大的 VM 也不能借旧小规格资格。每次均
重读原 immutable 对象 UID、完整内容/摘要、保护寿命与 Pod/Node 身份；不
扫描任选相同数值对象。当前 Root 的真实 MemTotal 只作“不低于原保证”的
检查，不用一次 MemTotal/RSS 或占用估计生产永久保证。

Root 聚合覆盖 PG 计费域及整个 Guest HugeTLB 池，只计一次，不把 Shared、
DSM、LFC 或池内已用/空闲再相加。Root 的历史 `OutsideUpperBytes` 是被聚合
排除的外部预留声明，不是系统硬限来源。v4 将准确规格的 Outside 独立计入，
不再要求它等于旧 Root 声明；当前有限系统硬限仍必须被认证 SystemOutsidePG
覆盖，完整去重预算不得溢出或超过准确 Guest 保证。旧格式校验保持。

生产组合实际覆盖了 target Outside 40MiB、旧 Root 声明32MiB的情形：Guest
取消后 Root normal 未改，VM 已到大规格，最终采用大规格的原40MiB来源。

## 收集、持久化、开放与完成顺序

1. 显式管理先取得必要的原 PG/VM/Guest 独立事实。Runner/Root 在自己的原
   文件锁内确认原效果或封存未收到命令；部分效果继续 Unknown，不重发或
   回滚资源，不用普通 NotFound 代替不可再发送的取消屏障。
2. 收集器认证同 VM UID/RV、当前 owner、原 Prepared、真实 Root/进程出生、
   Runner 完整来源与实际容量、准确 Outside、Host/Node 原峰值持有。
3. 再读 PG、Root、Runner 与来源对象，要求同一容量/Root/来源和当前门禁，
   最后同 VM UID/RV CAS 保存 `ServiceActualRecovery`。失败保留原预算和
   峰值，保存丢回复只重读同一证明，不选更便宜的新来源覆盖它。
4. 新开放写前、发送前后和最终完成前继续认证全部来源。普通轮询只查已
   保存选择，不创建新取消、Actual 预算或开放。门禁只能对应同 WAL 准确
   选择的原关闭、新开放、直接前驱关闭或异常再关闭，未知 revision 拒绝。
5. 完整新开放和当前有效原生期限确认后，完成 CAS 同时安装永久实际预算、
   原操作覆盖终态及预算水位，然后清 Active/当前关闭。单保存 Proof 或
   单收到开放回复不能提前退休原未知或退还 Host。

网络期间不持本地 mutex；Session 的串行执行通道、独立领域 fence、真实
Root/Runner 文件锁及最终 UID/RV CAS 分别负责自己的边界。SDK 的 mutex
仅保护原执行槽和相同 Pending 的检查/清除。原生 Fence 可推进隔离元数据，
不能称零 RPC 或零原生写；恢复不增加原 Resize、Guest Apply 或 QMP Set。

## 已保存终态后的缓存淘汰与 SDK 重建

原 PG 终态已单域保存，而原生缓存后来淘汰时，旧严格单域查询仍会拒绝将
完整终态改成缺历史隔离。旧路径若一直先查该单域，就无法创建完整预算。

现在首次无证明仍必须先保存 PG 对账；已有准确证明时，不重写它。收集器
仅允许与原完整 intent 一致的 SDK Pending 继续存在，FENCED 和全部当前
来源认证后先保存 Actual CAS；随后新 SDK 按完整持久预算、当前共享成本和
原 Key 查询再次核验，才清同一个 Pending。不同 Pending、执行槽替换或无
证明均拒绝。原 PG 尚 Planned 时没有可清的槽，仍须只读确认原 Key 未执行。

这里没有放宽旧单域 API；“来源证明已持久”与“SDK 当前执行槽已清”保持
独立。新窗口的明确协议 peer 覆盖单域完整终态保存→缓存淘汰→重建 Pending
→旧单域拒绝→正式 Actual/原 Key 复核清槽→重开/完成，原 Resize POST仅1次。
准确 PG17 的真实缓存门禁已通过，见下述精准原生验证；peer 与原生证据分别记账。

## 永久头、水位、Host 与有界来源寿命

新永久 `HeldCapacity` v3 使用 `ActiveRecovery` 保存完整原操作和独立实际
证明，Cleanup 必须零值；不伪造原 AbortReconcile/Finalize 完成。终态为
`RecoveredWithActualBudget`，与普通目标成功、原取消完成区分。原资源
Unknown 即使操作缓存淘汰仍永久保留在本头，预算 SHA 绑定完整实际预算，
不是零 Cleanup 摘要或旧命令摘要。

`CurrentCapacity()` 统一严格读取旧取消头与新 v3 头。普通循环、后继
Prepare/取消、Host 结清、Scheduler allocation 和 GC 不得继续只读旧
Cleanup 字段。预算边界/Through 水位与新完成点一起前进，已结清的旧峰值
不重新取得执行权；来源回收按永久头/活动操作/历史的准确引用保留原资格、
Outside、Runner 出生/State/回执，不能因缓存淘汰提前裁原命令 payload。

Host 在完整完成前继续持有 `max(before,target,actual)+overhead`。完整关闭
水位形成后才按实际 VM 容量结清。Scheduler 下一轮按当前永久预算及 Runner
实际读回，不回退旧 spec.Use。InitialVM 路径必须选择原 InitialVM 出生引用，
不能解引用零 Runner 来源或合成一次 VM Completed。

本批定向模型入口覆盖历史淘汰/后继取消后保留永久头，以及正常新 Finalize
原子替换旧实际头；原来源 GC、Host/水位受影响验证的最终采用根与数字由
统一收据列明，不将未执行的长期或 Linux 结果计入。本次还实际发现并修复
后继来源读取漏用 CurrentCapacity 的问题，并以真实 v3 前驱验证再次对账。
