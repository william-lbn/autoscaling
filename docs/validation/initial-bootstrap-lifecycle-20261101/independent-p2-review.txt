关键源码结论
1. 原进程：RunQEMU 独占同一 exec.Cmd，先 fsync 原 process-launch，再 freeze，随后唯一 Start；captureInitialBootProcess 在 Start 成功、唯一 Wait 前捕获原 pidfd 与 O_PATH procdir/start。checkPeer 在 SO_PEERCRED 读前后核原 pidfd 活性，并核当前四 UID/GID、原 exe dev/inode/hash；并不凭可重用 numeric PID 或 Unix socket 路径单独收养进程。cgexec 仍须是原受信 exec 包装，来源摘要不把任意程序认证成可信 QEMU。
2. 初次写顺序：linuxInitialLifecycle.drive 持原 engine flock，链只允许 source_frozen 单阶段开始；完整 prepared 原回执与原 reservation/owner 再核后，先追加 grow_prepared，再在真实 base/peer/原几何再核后追加 grow_may_have_sent。initialBootAppend 对既有整个前缀逐 file.Sync/dir.Sync，新增文件先写+file.Sync，再不替换 Linkat+dir.Sync；成功返回后才可执行唯一固定 vm0 requested-size qom-set。错误、丢回复或已推进链不自动重发；等于 base 的 no-op 不写 QMP。
3. 发布 gate：actual requested/actual 均到业务 Min，真实 Guest Movable 回执匹配后追加完整 typed complete，再发送 completion，随后仅本实例内存 ready 可开门。advance/publish 在原 flock 中核 gate；Read/Set 持原 processGuard、核本实例原进程/完整链/完成 entry。WAL 可见本身不能使重启 Runner 自动重获写权。普通 Observation/Set 仍保原业务 Min，不能使用初始低 base 绕过。
4. 生命周期收尾：初始 worker 失败仅向原 pidfd 发 SIGKILL；RunQEMU 唯一 cmd.Wait 消费原退出，stopAndWait 取消并 join 实际 worker，再独占 processGuard 关闭原句柄；保留原 may-have-sent 与 Host reservation，不将 QMP 断线或取消解释成已结清。完整初次交换成功后常规 QEMU 停机仍沿调用者原 exec.CommandContext/固定 powerdown/唯一 Wait 合同；本审查没有把初始 worker 的取消逻辑宣称通用生命周期控制器。
5. 版本：显式 InitialBootstrap 才生成 Birth/Publication v2；InitialMode 与 runtime/resource/config/kernel 原引用逐项绑定。v1 omit 新字段且明确拒出现新字段即使 null，失败出生/关闭来源同版本比较，既有 birth-intent/launch/WAL 不自动升级或重置。新 native adapter 在 Initialize 一次固定；不热换旧 native。
6. 设备与 CPU：固定启动参数拒 balloon/Xen、额外 monitor/HMP、替代 memory surface；原 SMP 与实际 hotplug inventory 交叉，实际 inventory 再拒 balloon。该组件只验证固定 argv/QMP 读回，不代表全部 future writer/source 已闭，也未授权将 F/I C64 基线改成 C2。
