# 原来源持有与有界回收：Mac阶段验收

本阶段沿`codex/dsga-autoscaling-20261019`演进，Neon沿原功能分支绑定。
准确源码/测试提交、逐文件SHA-256、逐用例结果、命令和日志摘要见
[机器收据](DSGA-原来源有界回收-Mac收据-20261029.json)。本批不修改PG17内核、
Rust和独立控制面，不追新上游、不构建镜像、不准备或执行K8s部署。

## 本批解决的问题

此前Host峰值已经可以按实际容量结清，但活动VM的旧Outside及Runner不可变
回执缺少回收路径；删除VM时的来源识别还会把平台资格视为未知类型，阻塞
原VM正常终结。仅将预算一直保留不能替代生命周期完成。

新增回收接在原Host完整结清之后，不是独立定时删除器。顺序为：认证原VM
无Active及永久预算/关闭水位，认证当前原Runner出生、原Lease和floor、
requested/actual、原资格与Node持有，再持久结清Host，最后发现旧来源。
没有这些事实时不进入清理；不会用超时、404、当前RSS或spec目标释放承诺。

## 必须保留与允许回收的界限

| 对象 | 保留/回收规则 |
|---|---|
| 当前普通/实际/初始预算的完整命令及回执引用 | 永久头独立扫描；历史淘汰不改变寿命 |
| 仍在16条恢复历史中的命令、Observation及Cleanup引用 | 保留到历史自身被正常淘汰，不能仅按Key旧就删 |
| Runner最后发布回执及完整Last的内容寻址对象 | 原State及Last均加入保留集合，包括发布回复未知时的原名称 |
| 原资格、Birth、State、ProcessExit | 活动VM不回收；资格属于可信配置/预算的根 |
| 已无以上引用的Outside及不可变Runner回执 | 必须同原VM/incarnation、Guest或Runner/Pod/Node、PG boot；原关闭水位已覆盖其完整Key |
| Host旧来源 | 继续原独立Host GC及关闭Through规则，不改变已有Host水位语义 |
| 未知版本、畸形、其他VM/boot/Pod/Node、同revision换operation ID | 保留，不把无法解释当作可以删除 |

保留集合显式遍历原payload。journal中命令/审计是`[]byte`，只marshal顶层
Model会得到base64并漏掉内部引用。本实现逐份解码已验证的原字节，再保守
收集嵌套ObjectRef；它仅计算保留集合，不认证来源。按名称保护同名替代对象，
缺原UID仍由业务受控恢复处理，GC不能清掉它后替业务重新创建。

每个候选都重新GET，核原UID、完整协议与原文摘要，再复核原VM RV/owner
Lease和Node持久结清水位。移除自己的finalizer使用JSON Patch UID/RV测试；
DELETE携带UID/RV条件。其他人的finalizer原样保留。PATCH或DELETE丢回复
交给后续实际读取恢复，不创建替代来源、不重发PG或QMP，也不回滚Host结清。

## 有界发现及资源开销

- 新增Outside/Runner扫描每页64条，每次最多读取两页、尝试清理16个来源；
  一个来源最多一次保护PATCH及一次DELETE，不是16次API写的上限。
- 每个Pod保存单个发现游标和最多一页小候选，只保留名称、UID、保护类型与
  摘要，不保存32KiB正文。避免256个Pod仅因持有分页正文就占约512MiB。
- 原VM或完整关闭水位改变立即丢弃发现游标；LIST token过期只重启本类发现。
  候选在尝试前出队，失败不饿死尾部；尾部扫完再从API重试原失败。
- Scheduler重建Publisher时复用该Pod的进度，进度表最多256项，可安全淘汰。
  进度不是任何许可；重启或淘汰只多做扫描，不能释放或重建原来源。
- 裸`ErrCollectionPending`只请求下轮继续，不触发一分钟“已完整扫描”缓存；
  同时携带真实API错误时继续报告。游标有并发占用保护，不跨网络持业务Mutex。
- 既有Host来源扫描沿用原实现与原10秒调用期限；本批新增的两类扫描采用上述
  独立有界分页，不把整个Host扫描也声称已重新实现。

## 原VM删除后的资格终结

Controller已有顺序仍成立：原Pod/QEMU关闭、Scheduler将关闭锚点写原VM、
全部Node不再持有该VM，才清来源保护。此时新增识别
`platform-qualification-v1`，与Outside使用同一预算来源保护finalizer。
原VM未有锚点、还有活动Pod/Node持有、Node换UID或未知来源版本时继续拒绝。
冷VM仍须满足原bootstrap从未开放/派发条件，不借本改动跳过关闭证明。

没有增加或放宽任何预算/VM/Node/Runner持久协议版本，没有把物理完成替换成
GC成功；默认关闭保持。旧程序不认识新清理逻辑时仍可能保守保留来源，不能
据此声称旧实现已经有该回收能力。PG17仍为冻结b078提交。

## 下一步与未验证边界

本批闭合上述旧操作来源回收及资格终结，不等于整个异常生命周期已经完成。
缺原来源/资格或Root不一致的受控恢复、安全降低normal及私有/后台持续上界、
真正VM owner切换、Start/init失败/无Wait/跨boot迁移、Monitor自动策略/可信
请求取消重放入口及全部写者/CPU隔离仍是代码或Mac组合工作。PG17核心完整
归档后继续PG18，再PG16；公共协议复用，各版内核/扩展/发行与专属回归独立。

Linux/K8s还必须验证真实RBAC、UID/RV/etcd/GC/finalizer、分页token与分区、
多VM长稳和删除竞态、NeonVM热插拔/退出、cgroup/HugeTLB与物理回收、存储/
性能。Mac通过不能保证这些正确。本批没有新Linux运行或ELF重编；未变PG/
Rust/GuestReady矩阵复用原证据。持续Goal保持active，阶段归档不等于整体完成。
