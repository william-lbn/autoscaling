问题与真实定位
ef57c0 的 idle CapacityHeld v3 恢复已确认 Rearm，但 Reopen 尚未写入。原完整 VM 的 Model.Validate 与 StartServiceReopen 纯模型均通过；真正 Store.apply 在 API Patch 前因编码预留拒绝，固定错误为 latest terminal result exceeds journal byte budget。不是据 HTTP503 或错误类型猜 Native/Proxy/VM 状态，也不据此认定现场所有历史错误同因。

统一修复
只改 journal codec 与私有 reserve helper，不改 Native DTO、协议、日志格式或执行器。先按原 Model.Validate 认证实例和 effective budget，再构造当前合法字段的类型长度支配形状。Snapshot 包含四数组、每个 ReleaseKey 与可共存 Operation；键的 Instance 由 Native.Validate 绑定同实例。所有 admission/closing/continuation 的预算由原 journal 强门绑定同一个有效预算，不接受调用方另造短身份。数字使用最大宽度；布尔 false 比 true 长；摘要按完整64位hex；最长已知枚举、optional 字段和重复 Request 不省略。

四个槽继续分别预留 AdmissionResponse、两份 AdmissionLeaseResponse，以及 max(AdmissionClosure, AdmissionContinuationResponse)；再关闭 Rearm 槽覆盖完整 AdmissionRearmStatus（含外层 Request 与 Current 内层 Request/Observed）。原外层 Rearm 36KiB预留不缩小。每槽加入原4096字节元数据余量，再考虑独立zlib流膨胀和base64成本，不把raw字节直接当编码注解字节。当前DTO字段结构有直接测试锁，改变DTO/枚举/约束仍须复核长度形状；不宣称未来任意改动自动安全。

必须保留的界限
该上界是完整类型的保守预留策略，不是整模型重新压缩的绝对数学完成保证。重压缩会改变字典匹配。每个阶段仍真实 encode 整个 Model，原192KiB encoded与1MiB raw总门不变；过大合法上下文仍可失败关闭，不能声称任意32KiB opaque正文都必可落账。预算拒绝不返回可派发票据，不能跳过 Native 原关闭、清 Unknown、释放预算或改变TTL。失败/丢CAS回复仍保原 Unknown；恢复/重试仍须原明确选择与权威Owner。
