## Linux 的单一主验证路线

1. 使用上述自有功能分支和精确锁，不追新上游；先确认实际源码、gitlink、两份锁及 `postgres --version` 一致。记录 Linux 架构、工具链、二进制 SHA 和执行环境到新收据，保留 Mac 历史收据。
2. 缺失代码继续在 Linux 完成。每批先列修改文件和调用链，只跑修改模块、受影响消费者及对应竞态/崩溃/旧格式拒绝场景。互不依赖的审查和测试可并行；同一账本变更、依赖提交及最终验收保持顺序。
3. 精确 PG17 原生层验证动态区分配/引用寿命/锁序、扩缩及真实物理回收、准入期限、在途登记/聚合预算和失败后保持未知。入口在 PG `src/test/modules/test_dsg_region` 与 Neon `ci/test_dsg_*.py`；从已变功能选择测试，禁止直接扩成官方 `check-world`。
4. Neon 修改层验证 `pgxn/neon` 的控制 SQL/角色/协议、`compute_tools` 的认证 Router/JWT/SDK/启动配置与 Monitor，使用准确 PG17 和私有实例；官方未改服务只按受影响接口参与组合。已有脚本可能固定较早的测试数，执行前核对实际测试名，不以零测试、过滤或环境跳过冒充通过。
5. Autoscaling 修改层验证 `pkg/api/dsga`、`pkg/dsga` 的 Journal/预算/管理恢复/来源生命周期，以及相关 Agent、Scheduler、Controller、Runner、Guest 最终写者。代表性真实正常扩缩和必要失败窗口串联完整链；先认证不可变来源与真实 UID/RV，再判断完成，不能用 VM spec PATCH 或 peer 回执代替实际资源完成。
6. 在现有获准目标环境验收 cgroup/进程约束、KVM/NeonVM/CRI、HugeTLB 与物理返还、Host 容量及相关负载/性能。保存“通过/失败/未执行”及实际范围；当前不构建镜像、不部署的边界继续保留，若现有环境缺少对应组件则该项仍未验收。

Linux 接续不重跑无修改且不受影响的官方存储、HA、迁移、其他 PG 大版本或独立控制面业务。PG18/16 和独立 CPU/组配额/RO 横向等产品扩展不进入本轮收口。
