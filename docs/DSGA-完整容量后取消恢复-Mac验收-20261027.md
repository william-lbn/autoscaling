## 本次完成的行为

这里的“完整容量后取消”有严格前提：原计划除ResumeAdmission外，所有步骤
均为Completed，且同一次FinalizeBudget的完整原预算已原子持有。取消不回滚
已成功的PG/Guest/VM容量，也不能把已有实际效果记成NoEffect。

1. 原Resume尚未派发时，核当前PG成本及fence、原Root限额/出生、Host/Outside/
   Runner来源和实际VM，再将独立恢复开放命令写入同VM Cleanup WAL，CAS确认后
   才发送。写后再次核所有来源及当前门禁代次，失败保留未知。
2. 原Resume已派发但未知时，先只读查询并落账原Resume，不能新建Cleanup覆盖
   未知；原Resume已完成时，Cleanup只查询这条原开放，绝不产生第二个setter。
3. Cleanup未知时普通轮询只查原命令。not-found、超时不自动重发；受信协调器
   可通过独立AbortReplay选择完整原Key，只有原派发owner能显式重放原命令。
   进程重建从该Cleanup恢复SDK pending，不能用重建客户端清掉未知。
4. Cleanup落账和Finish分轮，Finish前仍重读全部真实来源。Start/Record/Finish
   丢回复后读取持久事实，不重造命令或覆盖原审计。最终业务结果仍为
   AbortedAfterReconcile，完整BudgetHeld逐字保留。
5. 同一次Finish升级VM日志v6并记录容量关闭水位，使该真实成功容量在业务
   取消后仍有Host结清资格。水位能跨接管和短期历史淘汰；下一次派发仍立即
   撤销。通用Cleanup Completed、部分效果、其他预算或未知没有该资格。
6. Host Publisher继续核实际Runner/来源/Node，才将峰值结清为实际目标；旧Host
   回执不再提供执行授权。只有严格较旧、同一Pod且已失效的Host来源可清理。
