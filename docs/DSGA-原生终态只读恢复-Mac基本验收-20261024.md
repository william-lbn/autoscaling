## 修复的实际控制链问题

重建 PGWorker 时，已派发的 ResizePG 必须从完整 WAL 恢复 SDK Pending，即使
步骤已 Settled 也不能仅凭该枚举清未知。但是普通 Status 原本不清 Pending，
后续恢复准入又拒绝跨过 Pending，可能让已落账的原生 COMMITTED 永久挡住后续。
本批在实际 pgexec.Advance/Agent 循环加入原终态完整核对，不依赖人工重发 resize。

`compute.ReconcileTerminal` 接受完整原请求、原回执和当前 owner 的 FENCED：

- 先核验同一固定 PG boot、完整 context 摘要、真实原生终态和本地相同 Pending。
  普通 Status/Memory 行为保持只读且不清 Pending；关闭连接也不清。
- 仅请求原 Key 的 Status，要求 REPLAYED 完整回执、当前 floor、未早于 fence
  的观察代次，并比较原终态不可改变的身份、容量、generation、kind、目标、
  原因、取消状态及 context。历史结果和当前观察分别核对，不能拼接。
- Provider/保留成本、准入、当前 floor 后续可变化，不用旧终态替代当前预算。
  本方法不修改原 WAL、另一个 Pending、准入未知、资源承诺或 Host/VM 事实。
- 网络期间不持本地锁；读前与读后均核对同一 Pending 且没有执行在途。并发
  原 Resize 只能由其自身完整响应确认，不能被查询线程提前清除。
- not-found、expired、不同 context/终态、换 boot、更高 floor、旧快照均保留
  未知。Busy/Rejected 没有原生终态者不能借此清除，仍需受控关闭协议。

pgexec 先严格解析原 Step.Command、原审计和原 fence；只有 Completed/COMMITTED
或 Rejected/DENIED 对应才调用此恢复。先确认当前 PG floor，再只读核对。新增
`reconciled` 进度只代表 SDK 本地原栅栏已解除，不是 journal 写入、资源或 VM
完成；下一轮仍逐项核验原预算、Guest、VM 和准入。原 root 未知不阻断这个只读
PG 查询；原 owner 的较低 epoch 可以查询，但不改 epoch/PID/预算后重发。

## 范围与剩余

仅有完整原生终态的 Pending 可按此恢复；它不把未知结果当 NoEffect，不重写
Rejected 为成功，不自动关闭外层操作，不替代完整预算或首次准入。真实预算
Prepare/Finalize 生产者及 outside 权威、首次准入/全排空、Host/最终 Controller/
Runner/QMP、公开 worker/生命周期和受控跨 Guest/PG boot/owner 关闭仍需代码。
严格门禁有真实 PG 与生产 HTTP/SQL，但不是 K8s/RBAC、Guest/cgroup、HugeTLB、
Host/QMP 或物理端到端。Linux/K8s/内核/物理/性能后验。Goal active、默认关闭，
不构建镜像、不准备/执行部署、不合 main，不称整体完成。
